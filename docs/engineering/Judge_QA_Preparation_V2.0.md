## 一、技术评委问题

### Q1: 这不就是一个 LLM 加 Function Calling 吗？为什么说是 Multi-Agent？

**评委心理**：这是最常见的技术质疑。他在测试你是否真的理解 Multi-Agent 和单 Agent 的本质区别。

**30秒回答**：
> "如果是一个 LLM + Function Calling，它只能串行执行。我们展示的 Demo 中 Industry 分析、Risk 评估、Policy 匹配是**同时**执行的，这在时间戳上可以验证。而且每个 Agent 都有独立的 LangGraph StateGraph 实例——独立的 State Schema、独立的 Tool 权限、独立的错误处理。这是架构级的 Multi-Agent，不是 Prompt 级的。"

**2分钟回答**：
> "有三个硬性区别。
>
> 第一，**并行执行**。单 LLM 虽然可以调用多个 Function，但本质是串行的——调完一个等返回再调下一个。我们的 DAG Trace 可以证明：IndustryAgent 做完产业分析后，InvestmentAgent、RiskAgent、PolicyAgent 的启动时间戳相同——它们是真正并行的。
>
> 第二，**独立状态**。每个 Agent 有自己的 LangGraph StateGraph，自己的 State Schema。单 LLM 只有一个 Context Window——所有信息混在一起，越后面越容易遗忘前面的。我们有 6 个独立 Context，互不污染。
>
> 第三，**容错隔离**。如果 RiskAgent 因为数据问题出错了，其他 5 个 Agent 继续执行，最后报告标注'风险评估未完成，请稍后重试'。单 LLM 一个环节报错整个回复崩溃。这在企业场景至关重要——你不希望因为政策库更新延迟，整个招商报告都出不来了。
>
> 最后，我可以打开任意一个 Agent 的内部日志，展示它调用了哪些工具、每个工具返回了什么。这不是一个 Prompt 能伪造的。"

**防守要点**：直接说"请看时间戳"——这是证据，不是解释。

### Q2: 为什么需要 Supervisor？直接让 LLM 判断调用哪个 Agent 不行吗？

**30秒回答**：
> "Supervisor 的核心价值不是路由，是编排——它需要理解任务之间的依赖关系。'分析产业方向'必须在'推荐招商企业'之前，这是业务逻辑决定的。普通的 LLM Router 只能做'这个请求像什么类型'的分类，做不了任务 DAG 规划。"

**2分钟回答**：
> "举个具体例子。用户说'帮广州建机器人产业园'。
>
> 如果是一个 LLM Router，它会怎么做？它可能同时调用 Industry 和 Investment——结果 Investment 在没有产业方向指引的情况下，只能返回'所有机器人企业按注册资金排序'，这没用。
>
> 我们的 Supervisor 理解业务语义：'先搞清楚机器人产业链缺什么环节，再用这个缺口去筛选企业'。所以它规划的执行顺序是：
> ① IndustryAgent（串行，先做）
> ② InvestmentAgent + RiskAgent + PolicyAgent（并行，基于①的结果）
> ③ BIAgent（汇总）
>
> 这个 DAG 拓扑不是硬编码的，是 Supervisor LLM 根据任务语义推理出来的。不同的问题会生成不同的 DAG 拓扑。'
> 如何验证？打开 Trace 页面，可以看到 Supervisor 节点的输出里包含了完整的任务规划——每个子任务的依赖声明。"

### Q3: Agent 的可靠性如何保证？LLM 幻觉怎么处理？

**30秒回答**：
> "三层保障。第一层，LLM Gateway 有三模型 fallback——主模型挂了自动切换备选。第二层，每个 Agent 的输出都经过结构化 Schema 校验——不符合 Schema 的拒绝并重试。第三层，最关键的是数据层——企业数据、政策数据来自数据库，不是 LLM 生成的。LLM 只负责分析和推理，不负责生成事实。"

**2分钟回答**：
> "这是企业级 AI 最核心的问题。我们的方案分三层：
>
> **第一层：LLM 层可靠性**
> - LLM Gateway 主模型 DeepSeek → fallback GPT-4o → fallback 关键词兜底
> - 任何模型挂了都不会导致系统崩溃，只是精度逐级下降
> - 关键词兜底模式下至少保证数据结构正确
>
> **第二层：输出层校验**
> - 每个 Agent 的输出都通过 Pydantic Schema 校验
> - 例如 InvestmentAgent 输出的企业评分必须在 0-100 区间，违反就重试
> - PolicyAgent 输出的政策编号必须能反向查到原始文件
>
> **第三层：数据层隔离（最关键）**
> - 企业信息（名称、注册地、经营范围）来自 PostgreSQL 数据库——不是 LLM 编的
> - 政策文本来自预加载的政策知识库——不是 LLM 回忆的
> - 产业链图谱是手标注的——不是 LLM 幻觉的
> - LLM 的职责是**分析和推理**：分析趋势、推理缺口、评估匹配度
> - 事实数据不经过 LLM 生成
>
> 简单说：LLM 是大脑，负责思考。数据库是记忆，负责事实。我们不把两个混在一起。"

### Q4: 为什么不直接用 LangGraph 的 Checkpointing？自己实现 Agent 通信协议？

**30秒回答**：
> "我们用 LangGraph 做每个 Agent 的内部工作流，但 Agent 之间的通信我们设计了自己的 TaskMessage 协议。原因很简单：LangGraph 的 Checkpointing 是为单图设计的，跨 Agent 协调需要明确的消息契约——谁发起的、依赖谁、优先级、超时——这些 LangGraph 不提供。我们做的是 Agent 之上的编排层。"

**2分钟回答**：
> "架构分两层。
>
> **下层**：每个 Agent 内部用 LangGraph StateGraph 实现自己的工作流。这一步用 LangGraph 的原生能力——节点定义、条件边、Checkpointing。
>
> **上层**：Agent 之间的通信走我们的 TaskMessage 协议。为什么不直接用 LangGraph 的 Supergraph？
>
> 第一，**独立部署**。每个 Agent 可以跑在独立进程中，甚至独立服务器上。LangGraph 的 Supergraph 要求所有子图在同一个 Python 进程里。
>
> 第二，**消息契约**。TaskMessage 明确定义了 task_id、parent_task_id、priority、timeout、agent_name、payload——这在生产环境中是必须的。你需要知道哪个 Agent 调了哪个 Agent、超时了怎么办、失败怎么重试。
>
> 第三，**权限隔离**。每个 Agent 有自己的 Tool 权限集合。PolicyAgent 不能调用企业数据库的写操作，RiskAgent 不能修改政策数据。这是通过 Tool Gateway 的权限矩阵实现的，不是 LangGraph 的范畴。
>
> 我们用了 LangGraph 做引擎，但 Agent 之间的编排和通信是我们的核心创新。"

### Q5: 你们的技术栈为什么选择 DeepSeek？不是国产化吧？

**30秒回答**：
> "DeepSeek 就是国产模型。而且我们的 LLM Gateway 设计成模型无关——换模型只需要改一行配置。今天用 DeepSeek，明天可以切到通义千问、文心、GLM，Agent 逻辑完全不受影响。"

**2分钟回答**：
> "三个原因选 DeepSeek：
>
> 1. **性能**：在 Agent 编排场景中，DeepSeek 的 instruction following 能力和长上下文理解在国产模型中属于第一梯队。
> 2. **成本**：推理成本低，适合高频调用的 Agent 场景。
> 3. **但不是锁定的**：LLM Gateway 抽象层让我们可以切换任何 OpenAI-compatible 的模型。如果客户要求纯国产化——没问题，换成通义千问或者 GLM-4，Agent 代码一行不改。
>
> 关于国产化：国产化不等于只能用某个特定模型。我们的态度是提供选择。客户可以指定模型，也可以用自己的私有化部署模型。这是架构决定的自由。"

### Q10: 数据安全怎么处理？园区企业数据很敏感。

**30秒回答**：
> "数据不出园区。SaaS 版数据加密存储在独立租户空间。私有化部署版数据完全在客户自己的服务器上。而且 LLM 只分析数据，不存储数据——每次任务结束后上下文清零。"

**2分钟回答**：
> "三个维度保证：
>
> **存储安全**：
> - SaaS 版：每个客户独立 PostgreSQL Schema + 独立 pgvector namespace。不是混在一起的多租户数据库——是逻辑隔离的。
> - 私有化版：全部数据在客户自己的服务器上，我们只提供 Docker 镜像和更新服务。
> - 传输加密：TLS 1.3，API Key 鉴权。
>
> **使用安全**：
> - LLM 调用时，企业敏感信息（法人、联系方式）做脱敏处理后再传给模型。
> - Agent 调用的数据限制在任务所需的最小集合——PolicyAgent 看不到企业的完整财务数据。
> - Tool Gateway 权限矩阵：每个 Agent 只能调用授权范围内的工具。
>
> **合规安全**：
> - 符合《数据安全法》和《个人信息保护法》
> - 企业公开数据（工商注册信息）和内部数据严格分开
> - 审计日志完整记录每次数据访问——谁、什么时候、访问了什么
>
> 关键一句话：**LLM 是推理引擎，不是数据仓库。数据在数据库里，LLM 只能读取授权范围内的内容进行分析。**"

### Q12: 如果 AI 判断错了，谁负责？如何人工审核？

**30秒回答**：
> "AI 是辅助决策，不是替代决策。我们的设计原则是：AI 生成建议，人做最终判断。所有 AI 输出都有可追溯的数据来源，人可以反向验证。高风险决策（如大额投资建议）设置了人工确认节点。"

**2分钟回答**：
> "分三个层面：
>
> **设计原则**：
> - AI = 高级研究助理，不是决策者
> - 我们的定位是'AI 帮人更快做更好的决策'，不是'AI 替人做决策'
>
> **可验证性**（最关键）：
> - 每条 AI 分析结论都可以追溯到原始数据
> - 例如：'传感器缺口 40%' → 点击可看到产业链图谱各环节企业数量分布
> - 例如：'XX科技评分 92' → 点击可看到 6 个评分维度的子分数和权重
> - 人可以在 30 秒内验证 AI 的结论——因为我们记录了完整的数据链路
>
> **人工干预机制**：
> - 低风险操作（企业信息查询、政策检索）：AI 自动完成
> - 中风险操作（风险评估、企业推荐）：AI 给建议 + 数据依据，人确认
> - 高风险操作（大额投资建议、批量企业操作）：必须人工审批
> - 所有 AI 任务都有'申诉'入口——如果人对结果不满意，可以标记+反馈，用于持续优化
>
> **责任归属**：
> - 我们的服务协议明确：AI 提供分析和建议，最终决策由客户做出
> - 类似于 Bloomberg Terminal——它提供数据和工具，但不替你买卖股票"
>
> **防守策略补充**：如果评委追问"那出了错算谁的"，回答："我们提供全链路可追溯。如果 AI 的建议基于正确的数据做出了错误的推理——我们负责优化模型。如果数据本身有误——数据提供方负责。如果人无视 AI 的风险警告做了错误决策——人负责。AI 不是免责牌，但也不是黑盒。"

### Q13: 如何处理企业数据的隐私？园区之间数据共享吗？

**30秒回答**：
> "绝不共享。每个园区的数据完全隔离。我们的 AI 模型可以在不共享原始数据的情况下学习行业 Pattern——这叫联邦学习思路。但我们目前阶段不跨园区学习，每个园区数据完全独立。"

**2分钟回答**：
> "明确回答：**不共享。**
>
> **当前阶段**：
> - 每个园区是独立的数据库实例（或 Schema）
> - 没有数据混合、没有跨园区分析、没有'行业基准'计算
> - 客户数据 100% 隔离
>
> **未来可能的行业洞察服务**：
> - 如果未来提供'行业基准对比'（比如'你的招商效率在珠三角排第几名'）
> - 我们会使用差分隐私 + 聚合统计——只出结论不出原始数据
> - 且必须征得所有参与方的明确同意
> - 对于不愿意参与的客户，功能开关完全关闭
>
> **对比理解**：
> - Google Maps 知道你堵车 → 因为聚合了所有用户的 GPS 数据 → 但不会告诉别人'张三现在在哪'
> - 我们的行业洞察同理——'传感器企业平均入驻率 65%'这是聚合统计 — 不是'李四的园区入驻率 65%'
>
> 法律合规：所有操作符合《数据安全法》第 21 条（数据分类分级保护）和第 33 条（重要数据出境管理）。我们不碰重要数据，不出境数据。"
